# سیاست کلید AI برای معماری بدون سرور واسط

## تصمیم معماری

Smart Mechanic در نسخه فعلی از گوشی کاربر مستقیماً و از طریق اینترنت به سرویس هوش مصنوعی متصل می‌شود. در این معماری، سرور واسط اختصاصی برای پراکسی‌کردن درخواست AI اضافه نمی‌کنیم و ریسک قابل استخراج بودن کلید مشترک از APK را آگاهانه می‌پذیریم.

## ریسک پذیرفته‌شده

کلیدی که با `--dart-define=AI_API_KEY=...` در زمان ساخت Flutter به APK تزریق شود، داخل برنامه نهایی قابل بازیابی است. GitHub Secrets از افشای کلید در مخزن جلوگیری می‌کند، اما کلید را از APK نهایی مخفی نمی‌کند. Obfuscation نیز تضمین امنیت کلید نیست.

پیامدهای احتمالی:
- دیگران ممکن است کلید را استخراج کرده و خارج از برنامه از آن استفاده کنند.
- مصرف و هزینه API ممکن است افزایش یابد یا به سقف سرویس برسد.
- در صورت سوءاستفاده، چرخاندن یا جایگزین‌کردن کلید ممکن است لازم شود.

## اقدام‌های احتیاطی بدون افزودن سرور

1. کلید واقعی را در کد منبع، فایل‌های نمونه، لاگ‌ها، خروجی آزمون و پیام‌های خطا قرار ندهید.
2. کلید ساخت را فقط از GitHub Actions Secrets یا محیط امن محلی به build بدهید؛ این کار از افشای مخزنی جلوگیری می‌کند، نه از استخراج APK.
3. در داشبورد ارائه‌دهنده AI، سقف هزینه/مصرف، هشدار مصرف و محدودیت‌های قابل‌تنظیم را فعال کنید.
4. در برنامه timeout، مدیریت خطا، محدودیت معقول اندازه ورودی و جلوگیری از درخواست‌های تکراری ناخواسته را حفظ کنید.
5. اگر کلید در مخزن یا گزارش عمومی منتشر شد، آن را فوراً باطل و جایگزین کنید. با توجه به ریسک پذیرفته‌شده، برای سوءاستفاده از APK نیز امکان چرخاندن کلید را در نظر داشته باشید.
6. کلید را در گزارش عیب‌یابی یا مستندات ثبت نکنید و خطاهای شبکه را بدون نمایش هدرها یا اطلاعات محرمانه ثبت کنید.

## محدوده تصمیم

این سیاست به معنی امن‌بودن کلید داخل APK نیست؛ فقط تصمیم آگاهانه برای حفظ معماری مستقیم و بدون سرور واسط را ثبت می‌کند. اگر بعداً هزینه یا سوءاستفاده مشکل‌ساز شد، باید دوباره درباره پراکسی سمت سرور یا کلید اختصاصی هر کاربر تصمیم‌گیری شود.
